## Execution Record

### Scope Completed

1. Added a shared runtime-registration source used by GameHost discovery, GameManager session startup, and runtime asset resolution.
2. Preserved the established `runtime-game-registrations.json` format and `STORYBOARD_RUNTIME_GAME_DISCOVERY_JSON_PATH` seam.
3. GameHost now creates one registration source and passes it to discovery, session/runtime services, and asset management so all three consumers resolve the same catalog path and identity source.
4. Session startup now canonicalizes the session `GameId`/`GameKey` from the matched enabled registration entry and rejects conflicting identity pairs.
5. Host health/readiness now reports registration-source readiness and returns HTTP 503 when the configured catalog cannot be loaded.
6. Production GameHost startup ignores the environment-selected development registration override; the durable configured catalog remains the source outside Development.
7. Existing session duplicate-start, end/restart, port binding, and loopback behavior remains intact; process reuse, restart arbitration, orphan cleanup, and launch correlation remain Designer launcher responsibilities.
8. Added explicit `allowPasswordlessLogin` support to JSON-backed host principals. A principal with that flag enabled and an empty configured password may authenticate with a username and no password; an empty password without the explicit flag remains rejected.
9. Deployment/environment gating for passwordless principals is intentionally deferred by decision and is not part of this readiness pass.

### Contract/Interface Impact

1. No `Storyboard.Contracts` or transport schema changes.
2. The new registration source is an engine/host implementation service, not a cross-repository launch manifest.
3. Existing discovery, session, asset, and health routes remain in use. The health route is `GET /api/v1/health`; it adds readiness metadata and uses HTTP 503 for an unavailable registration source.
4. Passwordless authentication is configuration-backed in the existing JSON identity provider; no transport contract change is required. The Portal still receives and uses the normal short-lived credential handle after authentication.
5. The configuration shape is explicit: `{ "username": "dev", "password": "", "allowPasswordlessLogin": true }`. Username-only authentication is accepted only when `allowPasswordlessLogin` is `true` and the configured password is empty; omitting the flag or setting it to `false` preserves the existing password requirement.

### Remaining Gaps

1. Designer still owns temporary catalog-file creation, child-process launch, port allocation/reuse, browser startup, retry, and orphan cleanup; those are F01.2 scope.
2. The health endpoint validates that the selected catalog can be loaded, but does not validate that the registered runtime export is loadable until discovery/session startup. F01.2 should consume both readiness and actionable startup failures.
3. The existing default catalog remains durable host configuration; no production catalog mutation or temporary-file cleanup is implemented in this Host/Engine pass.
4. Passwordless-principal deployment hardening is deferred; future product-deployment work must decide whether and how to restrict `allowPasswordlessLogin`.
