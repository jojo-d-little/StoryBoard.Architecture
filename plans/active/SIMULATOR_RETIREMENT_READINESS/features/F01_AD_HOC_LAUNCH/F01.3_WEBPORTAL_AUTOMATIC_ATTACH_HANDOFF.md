## Purpose

1. Use existing host/session behavior to make WebPortal enter the intended development bootstrap after Designer launch, with session start/attach governed by explicit policy rather than game-count inference.
2. Do not add browser filesystem access or assume a new transport contract.

## Preconditions

1. F01.1 host behavior and F01.2 launch context are complete.
2. Read existing Portal discovery/session flow before proposing a new interface.

## Designer Launch Context

When Designer launches the development WebPortal, it opens the host-served bundle with this same-origin URL shape:

`http://127.0.0.1:<port>/client/?mode=devsimulator&username=<url-encoded-user>&autoStartSession=true`

1. `mode=devsimulator` is the explicit Portal UI mode. The Portal resolves this mode through its orchestration mode configuration to select the form factor, skeleton layout, and composition profile. It does not by itself authorize authentication or session startup.
2. `username` is the machine-local Designer preference `DevelopmentUsername`; it defaults to `dev` and is non-secret. Its presence requests username-based automatic authentication.
3. `autoStartSession=true` is the explicit request for automatic discovery followed by session start/attach. Without this parameter, username bootstrap may authenticate but must not automatically start a session.
4. No password, bearer token, or credential handle is passed in the URL. Portal must use the username with the approved development GameHost authentication flow and receive a short-lived credential handle from GameHost.
5. GameHost discovery is expected to return the one enabled registration created by Designer. When `autoStartSession=true`, Portal may select that sole game automatically after successful authentication/discovery; zero or multiple enabled games must stop the automatic path rather than guess.
6. The automatic session operation currently invokes the existing start-session interface, which creates a session or attaches to a compatible existing owner session returned by GameHost. This is documented as session start/attach rather than a separate explicit join request.
7. Automatic session start/attach is held until the Portal startup-audio gate is ready. A successful welcome sound must finish before Portal invokes the session operation; an explicit user choice to continue muted is the alternate ready state. `autoStartSession=true` requests the flow but does not bypass this gate.
8. The JSON identity provider supports an explicitly opted-in passwordless principal through `allowPasswordlessLogin`; no password value is required for that principal. Production/deployment gating is intentionally deferred.

## Execution Record

### Scope Completed

1. Portal recognizes the explicit `mode=devsimulator` value, loads the corresponding orchestration mode policy, and resolves its form factor, skeleton, and composition defaults.
2. Portal initializes the development authentication flow with the URL-encoded username and an empty password, then uses the returned short-lived credential handle for subsequent requests.
3. Portal performs automatic discovery and selects/starts the sole enabled discovered game only when `autoStartSession=true`. Zero discovered games and multiple discovered games stop the automatic path with visible status and diagnostics rather than guessing.
4. Portal treats `Session.Start.AlreadyExists` as an attachable result only when the returned descriptor identifies the current principal as both joined and owner. It attaches the existing session locally without resetting the host session; a newly created session follows the existing start-session path.
5. The launch query remains in the address bar so a failed bootstrap can be retried and the launch intent remains diagnosable.
6. Portal always uses the configuration-driven renderer. The obsolete `rm` renderer parameter and Shell Lab renderer path are removed; internal layout overrides remain a temporary developer mechanism until the interactive Dev Tools controls fully replace them.

### Contract/Interface Impact

1. No new transport contract is required for passwordless sign-in; the behavior is configuration-backed in the existing host identity provider.
2. The Portal must still submit a configured username and use the returned short-lived credential handle for subsequent requests.
3. Environment/deployment gating for passwordless principals is intentionally deferred from this readiness pass and must be revisited during product-deployment hardening.
4. The browser handoff now adds the explicit non-secret boolean `autoStartSession=true`; no browser filesystem handoff, bearer token, or credential-handle transport is introduced.
5. `mode` is now consumed by the Portal orchestration resolver through `portal-modes.v1.json`; Designer still passes only the semantic mode key, not internal layout keys.
6. `rm` is removed from the Portal handoff and runtime renderer selection. The configuration-driven renderer is always used.
