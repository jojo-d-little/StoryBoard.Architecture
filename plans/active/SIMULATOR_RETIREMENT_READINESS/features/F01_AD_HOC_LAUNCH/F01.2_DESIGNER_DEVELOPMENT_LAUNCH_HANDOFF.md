## Execution Record

### Scope Completed

1. Added a distinct `Run Development WebPortal` Designer action beside the unchanged `Run Simulator` action.
2. The development action saves/validates/exports the current project, creates an invocation-scoped one-entry `runtime-game-registrations.json`, and starts GameHost in `Development` with `STORYBOARD_RUNTIME_GAME_DISCOVERY_JSON_PATH` and `STORYBOARD_WEBPORTAL_ROOT` overrides.
3. GameHost receives existing configuration keys for an allocated loopback port and `LoopbackOnly` binding; Designer waits for HTTP 200 `GET /api/v1/health` with `runtimeRegistrationReady=true` before opening the development bootstrap URI in the system browser.
4. Development identity is deterministic for the canonical project path: `GameId` is derived from SHA-256 bytes and `GameKey` is `designer.dev.<hash>`. Registration uses `local-tenant` and `local-org`, remains one-entry and enabled, and points at the exact absolute runtime export.
5. Every `Run Development WebPortal` invocation stops any prior Designer-owned host and starts a fresh host with a new temporary registration file and loopback port. Readiness failure, browser-open failure, cancellation, and application shutdown stop the child process and remove the temporary registration file.
6. The exact F01.3 launch context is the returned host base URI, browser URI (`http://127.0.0.1:<port>/client/?mode=devsimulator&username=<url-encoded-user>&autoStartSession=true`), deterministic `GameId`, deterministic `GameKey`, and registration file path for bounded diagnostics. Portal remains responsible for discovery/session start/attach.
7. Host/Engine owns the explicitly configured passwordless principal through `allowPasswordlessLogin`; Designer only supplies the configured non-secret username to Portal and never supplies a password or credential handle.
8. The browser URI contract now requires explicit development UI mode and bootstrap intent: `http://127.0.0.1:<port>/client/?mode=devsimulator&username=<url-encoded-user>&autoStartSession=true`. The Designer implementation must append `autoStartSession=true` when launching the automatic development session flow.
9. `username` comes from the machine-local Designer preference `DevelopmentUsername`, defaults to `dev`, and is URI-encoded. `autoStartSession=true` explicitly authorizes Portal discovery followed by automatic session start/attach for the sole discovered game. `GameHostExecutablePath` and `WebPortalRootPath` are also machine-local Designer preferences exposed by `Development WebPortal Setup`; both are optional, and blank values preserve automatic discovery/environment fallback. Designer never passes a password or credential handle; the Portal and GameHost own the authentication exchange.
10. The Designer output console records the resolved GameHost executable, working directory, visible-console state, complete command display, numbered raw arguments, and non-secret environment overrides (`DOTNET_ENVIRONMENT`, `ASPNETCORE_ENVIRONMENT`, registration JSON path, and WebPortal root) for each fresh launch result, including readiness failures. The development GameHost is launched with a visible console window so live host logging can be monitored during WebPortal testing.
