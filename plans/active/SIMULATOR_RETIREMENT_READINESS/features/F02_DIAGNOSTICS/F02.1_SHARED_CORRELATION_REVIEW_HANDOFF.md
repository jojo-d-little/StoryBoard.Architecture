## Purpose

1. Establish the minimum shared correlation convention needed to align Portal, Host, and Engine traces later without creating an oversized diagnostics contract.

## Preconditions

1. Read the F02 feature packet and F02 section of the execution roadmap.
2. Review the existing `HostRequestContext`, command-correlation, session, delta-watermark, and Engine trace fields.
3. Confirm that the future merge utility is deferred and that F02 Portal capture remains client-side only.

## Authorized Scope

1. Primary area: `StoryBoard.Contracts/Storyboard.Shared.Contracts/**` for review or additive contract changes only; related existing Engine and Portal fields may be inspected read-only.
2. Inherit `01_CONTRACTS_SHARED_PROFILE.md`.
3. Do not implement Portal capture, Host logging, Engine tracing, or the merge utility in this pass.

## Required Output

1. A short approved convention for `CorrelationId`, `RequestId`, `SessionId`, `GameId`, `CommandCorrelationId`, `SessionDeltaWatermark`, `GameTick`, and UTC timestamps.
2. A disposition stating whether an additive contract change is required. The starting expectation is no new transport contract.
3. Exact consumer guidance for F02.2 and later alignment work.

## Validation

1. Contract/schema/code-generation guardrails if any contract file changes.
2. Review existing producers and consumers to verify that the proposed convention is compatible and additive.

## Execution Record

### Scope Completed

1. Reviewed the existing shared `HostRequestContext`, command request/result metadata, session descriptors, session-delta watermark, Host transport tracing, Engine core-flow tracing, and Portal diagnostics/client surfaces.
2. Confirmed that the existing `HostRequestContext.CorrelationId` is the canonical logical-operation correlation field; no new shared trace identifier is required for the MVP.
3. Confirmed the supporting meanings: `RequestId` identifies one HTTP attempt, `SessionId`/`GameId` scope the activity, `CommandCorrelationId` identifies a command lineage, `SessionDeltaWatermark` identifies a delivered session-state boundary, and `GameTick` identifies an Engine-local simulation position.
4. Confirmed that timestamps are ordering aids only. Cross-system alignment must use correlation and scope metadata first, with UTC timestamps and source order as fallbacks.
5. Confirmed that autonomous Engine activities such as timers and published events do not require a client correlation ID. They already use Engine-local activity correlation IDs and should retain session/game/tick context; parent client correlation can be added later when causality is worth preserving.
6. Deferred the three-log merge utility. F02 will preserve useful metadata and produce a strong Portal trace, but will not implement aggregation or automated merge ordering.

### Files Changed

1. `F02.1_SHARED_CORRELATION_REVIEW_HANDOFF.md` — architecture decision and consumer-gap record only.

### Contract/Interface Impact

1. No `Storyboard.Contracts` schema or transport DTO change is required for the MVP.
2. Existing fields remain the approved shared surface; consumer implementations must standardize their values and propagation.
3. A future contract change would require a demonstrated need to expose new data across a boundary, such as Portal-visible Engine tick or autonomous-origin metadata.

### Validation Results

1. Reviewed `HostRequestContext_contract.cs`, existing command/session/delta contracts, `RuntimeCoreFlowTraceEntry`, `RuntimeEngineTraceLogger`, `HostTransportTraceLogger`, `HostApiClient`, and `DiagnosticsEntry`.
2. Confirmed that the current delta watermark is a session-delta journal sequence and is not the same value as `GameTick`.
3. Confirmed that Engine timer, event, and think-loop traces already have local correlation identifiers.
4. No product tests were required for this review-only pass; `git diff --check` is the applicable validation.

### Remaining Gaps

1. Portal currently uses fixed method labels for several request `CorrelationId` values rather than unique logical-operation identifiers; F02.2 must resolve the Portal-side convention.
2. Portal diagnostics entries do not yet preserve request/session/command/watermark metadata in a structured form; F02.2 must include the metadata available at each event site.
3. Portal does not currently send the Host transport `X-Correlation-Id` header, while Host transport tracing primarily resolves correlation from that header or the server request identifier; this consumer alignment must be routed during implementation/integration.
4. Engine core-flow trace output currently uses local-time formatting in its CSV line writer; UTC normalization should be handled before any future automated merge utility.
5. A later integration pass must verify how Host request correlation, Engine command correlation, Portal command results, and delta watermarks align in captured files.
