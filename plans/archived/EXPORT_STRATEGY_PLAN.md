# Export Strategy Plan

Last updated: 2026-06-22

## Purpose
This is the long-term plan for export architecture in StoryboardDesigner.

Primary goals:
- Deliver a stable, clean, versioned standard export for external collaboration.
- Keep authoring persistence flexible for editor needs and backward compatibility.
- Enable future custom export formats without destabilizing core save/load.

## Core Direction (Decision)
Use a three-file-class approach:
1. Native user project data files remain the source of truth for authored content.
2. Native application state data files store tool/session behavior metadata.
3. Clean exported format files provide the external integration contract.

Future custom formats will be generated from the clean exported format, not directly from native files.

## Scope
### In scope now
- Define and implement standard export contract v1.
- Remove editor and legacy noise from standard export outputs.
- Add contract tests and validation for standard export stability.

### Out of scope now
- Generic plugin runtime for third-party transforms.
- User-authored scripting for arbitrary transformation logic.
- Full custom transform UI.

## Guiding Principles
1. Contract-first: standard export is an interface, not a mirror of editor internals.
2. Backward-safe authoring: existing project files must continue to load.
3. Deterministic output: same input model must produce same output layout/order.
4. Explicit versioning: schema version declared and governed.
5. Progressive extensibility: add transform flexibility only after contract v1 is stable.
6. Data-classification separation: authored project content and application/workspace state are stored separately.

## Data Classifications (Required Separation)
### Class 1: Native User Project Data
Definition:
- Data intentionally authored by the game/content designer.

Examples:
- Planet/country/area/room/object definitions.
- Commands, actions, links, variables, message scripts.
- Runtime-relevant gameplay metadata.

Storage rule:
- Stored in native project authoring files.
- This data is eligible to flow into the clean exported format.

### Class 2: Native Application State Data
Definition:
- Data about editor/session behavior rather than game content.

Examples:
- Selected tabs/panels, tree selection, splitter positions.
- Window size/location.
- Recent projects list.
- Last-opened context convenience metadata.

Storage rule:
- Stored in separate state files outside core authored content files.
- Never included in the clean exported format contract.

### Class 3: Clean Exported Format Data
Definition:
- Contracted, collaboration-ready representation derived from native user project data.

Examples:
- Runtime-relevant room, object, action, navigation, and variable data required by consumers.

Storage rule:
- Generated by export workflow.
- Excludes native application state data.

Rationale:
- Prevents authored content from being polluted by machine/session noise.
- Reduces merge churn and collaboration confusion.
- Allows app UX evolution without touching project content schema.

## Pre-Export Prerequisite: Native File Debt Cleanup
Objective:
- Clean authoring/native files before implementing standard export v1 so debt does not leak into the contract.

Execution sequence:
1. Inventory and classify debt fields.
2. Add/adjust save-load regression tests for current behavior.
3. Stop writing low-risk debt/legacy fields.
4. Split Class 2 native application state out of Class 1 native user project files.
5. Migrate and normalize all controlled sample files to current intended shape.
6. Decide whether to remove backward-compatible read support now (pre-user-base window).

Step 6 decision gate (new):
- Because there is no external user-base yet and sample files are fully controlled, this is the best time to consider removing legacy read fallbacks.
- If we remove fallback readers now, require:
  - all sample/test fixtures migrated,
  - a one-time breaking-change note,
  - explicit lock-in date after which backward reads are not guaranteed.
- If we keep fallback readers now, timebox and revisit after first production usage milestone.

Recommended default for this project stage:
- Prefer removing backward-compatible read support for clearly obsolete structures after sample migration is complete, to reduce long-term maintenance overhead.

Implementation note for state split:
- Introduce a dedicated project-state sidecar file (for example, `<ProjectName>.sbe.state.json`) for Class 2 data that is project-specific.
- Keep machine-wide state (for example, recent projects and window placement) in existing app-level state files.
- Keep load behavior tolerant during transition: if legacy state exists inline in project file, import it once and rewrite to sidecar.

## Phase Plan

### P0: Contract Framing and Cleanup Decisions (Detailed)
Objective:
- Lock down what belongs in standard export versus authoring-only persistence.

Checklist:
- [ ] Confirm Class A/Class B classification table and storage boundaries.
- [ ] Confirm Step 6 outcome from native file debt cleanup (remove or keep legacy read support).
- [ ] Define canonical standard export file set and naming.
- [ ] Define required top-level metadata including schema version.
- [ ] Classify persisted properties as runtime-required vs authoring-only.
- [ ] Mark legacy compatibility fields that should stop being written in new standard export.
- [ ] Approve deprecation policy for removed/noisy fields.

Initial classification candidates (from current review):
- Authoring-only likely:
  - uiState
  - selectedWorkspaceTabIndex
  - producerNotes (unless explicitly required by downstream runtime)
- Application/workspace state likely (Class B, split to sidecar/app state):
  - uiState
  - selectedWorkspaceTabIndex
  - future panel/splitter layout metadata if added
- Legacy/compat baggage likely:
  - inline area links/rooms in main project file when sidecars already carry this
  - object command string list if not used in runtime command resolution
- Runtime contract likely:
  - room/action/message script/variable data used by command processing and script evaluation
  - navigation links needed for movement

Deliverables:
- [ ] Class A/Class B boundary table (field-by-field classification).
- [ ] Contract boundary table (field-by-field classification).
- [ ] Standard export v1 draft specification.
- [ ] Migration/backward-compat notes for authoring load path.

Exit criteria:
- Team signs off on export v1 boundary and field list.

### P1: Standard Export v1 Implementation (Detailed)
Objective:
- Implement a dedicated standard export writer from the in-memory model.

Implementation notes:
- Keep existing authoring save/load behavior intact.
- Introduce explicit standard export command/workflow path.
- Keep standard export DTOs isolated from authoring DTOs.

Checklist:
- [ ] Add new standard export DTO model namespace (v1).
- [ ] Add schemaVersion in standard export root metadata.
- [ ] Implement model-to-standard-export mapping service.
- [ ] Ensure deterministic ordering for arrays (ids/names as agreed).
- [ ] Omit null/default/empty fields per contract policy where safe.
- [ ] Keep compatibility readers for old authoring files unchanged.

Recommended first output profile:
- [ ] Standard engine-neutral JSON export profile only.

Deliverables:
- [ ] Export service implementation.
- [ ] Sample exported bundle from current fixtures.
- [ ] Developer notes on deterministic ordering rules.

Exit criteria:
- Standard export runs end-to-end and outputs clean v1 files from existing projects.

### P2: Validation, Tests, and CI Safety Rails (Detailed)
Objective:
- Make standard export safe to evolve without accidental contract regressions.

Checklist:
- [ ] Add snapshot/golden-file tests for representative project fixtures.
- [ ] Add schema validation tests for exported files.
- [ ] Add regression tests proving omitted authoring-only fields are not emitted.
- [ ] Add deterministic export test (repeat export byte-for-byte or semantically equivalent).
- [ ] Add reference-integrity checks (ids, links, action references).

Quality gates:
- [ ] Contract changes require schema version decision.
- [ ] CI fails on golden diff without approved update.

Deliverables:

- [ ] Export validation report (manual or automated).

- Standard export v1 considered stable for external integration.

Objective:
- Move external sharing to standard export while preserving authoring continuity.

Checklist:
- [ ] Document standard export as the collaboration interface.
- [ ] Update team workflow to share standard export artifacts, not raw authoring files.
- [ ] Add release notes template for export contract changes.
- [ ] Add compatibility statement (supported schema versions).

Deliverables:
- [ ] Collaboration handoff guide.
- [ ] Versioning and deprecation policy summary.

Exit criteria:
- Engine collaboration uses standard export v1 by default.

---

### P4: Future Custom Transform Capability (Loose Direction, Not for Immediate Implementation)
Objective:
- Enable additional external formats derived from standard export.

Direction only:
- Start with declarative export profiles (mapping/filter/rename/value normalization).
- Keep adapter types bounded (avoid arbitrary runtime scripting initially).
- Validate profile compatibility against standard export schema versions.

Possible staged path:
1. Declarative profile runner (JSON-to-JSON transforms).
2. Additional built-in adapters for templated outputs.
3. Optional advanced extension point only when concrete needs exceed declarative model.

Non-goals in early custom phase:
- No plugin marketplace.
- No unrestricted code execution in transforms.

Success signal:
- New external format added via profile/config with minimal core code changes.

## Risks and Mitigations
Risk: Contract drift from ad hoc field additions.
Mitigation: Require export contract review and schema version policy.

Risk: Over-optimizing flexibility before v1 stability.
Mitigation: Defer custom transforms until P0-P3 are complete.

Risk: Breaking legacy projects while cleaning output.
Mitigation: Keep load fallback paths for legacy authoring structures.

Risk: State split creates confusion about where settings live.
Mitigation: Document state file boundaries clearly and keep naming conventions explicit.

Risk: Prematurely removing backward reads creates migration pain.
Mitigation: Remove only after fixture migration, test pass, and explicit one-time break notice.
